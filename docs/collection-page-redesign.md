# 采集页面重新设计讨论

2026-11-23。状态：设计及四项拆分已由用户确认并授权发布、实现和端到端验证。规格 GitHub #29，子任务 #30–#33。

## 已核实的问题

- 资产采集页面把基础采集与容器目录放在同一表单的采集选项中。默认基础采集；没有 Docker 授权时，容器目录选项不会出现，用户无法发现缺少什么配置。
- 基础采集取得主机信息、系统包和直接可得的软件版本；Docker CLI 版本属于版本资料。容器与镜像目录是独立采集范围；镜像内部组件生成和漏洞评估又是后续操作。
- 单个 allowDocker 授权同时控制基础采集中的引擎版本查询及容器目录读取，界面没有清楚解释其用途。
- 当前 local 执行指 YS 后端部署主机，不能访问浏览器所在电脑。网页只能创建 SSH 连接，本机执行连接需要服务端静态配置。
- 容器镜像页面已有发现目录、选择固定 ImageID 生成 SBOM、评估、手动上传和离线脚本入口；应避免设计第二套重复流程。
- 术语表已将基础采集、组件采集、风险评估分别定义，当前困惑主要来自页面组织与执行目标不明确。

## 第一轮决策树（已确认）

1. “本机”与执行位置：明确区分 YS 部署主机、其他受管主机、操作员电脑。部署主机可提供受控本机执行；其他主机使用 SSH；操作员电脑可 SSH 或目标机离线执行后上传。网页不自动取得浏览器电脑的 Docker。
   - 入口、绑定与检查方式已由第二轮明确，平台范围已确认首版 Linux + Docker。
2. 页面任务划分：资产采集页将“主机基础资料”“容器运行资料”作为并列可见任务；连接配置及采集历史为公共区域。Docker 目录能力不可用时仍显示入口及原因。
   - 主机基础资料：主机身份、OS、硬件、系统包、软件版本；无容器实例/镜像目录。
   - 容器运行资料：Docker 引擎、镜像目录、容器实例及关联；按目标和连接检查权限，不要求 Trivy。
   - 镜像组件与漏洞评估：保留在容器镜像页，从固定目录提供直接跳转并带入主机/快照，避免重复选择。
   - 默认流程、布局及资料入口已由第二轮明确；连接授权兼容及失败处理已确认，具体验收随任务拆分。

## 第二轮细节（已确认）

1. 本机执行入口：部署端显式登记并启用 YS 部署主机，网页可选择该执行位置并绑定允许的客户/资产；显示实际执行主机及身份，提供连接与能力检查。不能把任意客户资产直接绑定到部署主机。本机权限不足时说明原因，不自动安装或提权。
2. 页面布局：顶部统一选择目标主机和执行位置，中部并列“主机基础资料 / 容器运行资料”，各自有独立动作、资料状态与覆盖说明；首次默认主机基础资料，从其他页面跳入时按任务定位。连接配置收进单独面板，底部统一历史可按类型筛选。主机基础流程不再请求 Docker 引擎访问；Docker CLI 软件版本仍可作为已安装软件版本记录。
3. 离线与人工入口：两种采集任务都提供在线采集、离线脚本和上传结果；下载脚本按任务区分，统一显示目标、时间、来源与缺口。容器目录仅由真实采集结果导入；人工登记不能声明为已发现运行实例。镜像 SBOM 沿用容器镜像页面导入。

## 执行与兼容（已确认）

- 目录发现成功后展示镜像和实例，不自动生成或扫描全部镜像；选定镜像后显式进入现有镜像生成流程，带入客户、主机、连接和固定快照。
- 能力检查区分“未授权”“工具缺失”“访问失败”“未检查”“可用”。Docker 不可用不阻断主机基础采集；无 Trivy 仍可发现目录。检查结果记录时间，发起任务前重新核验授权与目标。
- 保留原有连接、客户/资产绑定、采集历史及原始来源，不自动扩展 Docker 授权。已有 Docker 授权平移到新界面的容器能力；旧基础观测中的 Docker 字段仅作历史资料呈现，不改写旧证据。
- 首版覆盖 Linux + Docker；现有基础采集适配 Linux，Docker 使用目标主机固定 socket，不声明支持 macOS Docker Desktop 或 Windows 原生采集。

## 平台及迁移（已确认）

- 平台范围：首版在线和离线主机/容器目录采集覆盖 Linux + Docker；YS 部署主机作为本机执行验收目标。操作员电脑为 macOS Docker Desktop 或 Windows 时，本轮不声称完整采集支持，仍可上传已有镜像 SBOM；跨平台采集适配单列后续范围。如用户要求本轮支持，需分别明确宿主机和 Docker 虚拟机身份、socket/context、软件包覆盖及真实环境验收。
- 迁移：保留旧连接、历史快照及原始来源，旧 allowDocker 授权沿用，不自动扩大；无授权时入口保持可见，给出原因和配置路径。Docker 不可用不阻断基础采集，无 Trivy 不阻断目录发现。

## 已发布任务拆分

1. 独立完成 SSH 主机基础采集。无前置任务。统一目标/连接区、并列任务入口、基础能力检查、独立基础采集及历史；基础流程不访问 Docker 引擎。
2. 独立完成 Docker 目录发现并进入镜像生成。依赖 1。容器能力及失败原因始终可见；Docker/Trivy 分别检查，目录结果可携固定来源跳转既有镜像生成。
3. 网页选择已登记的 YS 部署主机完成本机采集。依赖 2。受控登记与客户/资产绑定、执行身份显示、本机两类任务能力检查与执行、跨客户及跨目标校验。
4. 两类 Linux 离线脚本下载、执行、上传及历史回读。依赖 2。脚本按范围区分，原始产物和来源校验、上传归属确认、重复/损坏/不支持资料处理，容器结果延续到镜像页面；离线导入不自动赋予在线访问授权。

每项均包含公共 API、界面及端到端验收，并保持旧连接、授权和快照兼容；桌面/手机、刷新、客户隔离、历史证据回读属于各项验收。3 与 4 可并行。发布时使用 niwaip/ys GitHub Issues、ready-for-agent 标签、原生阻塞关系和规格父任务关联。

## 实现契约

- `POST /collections/capabilities`：assetId、profileId、scope。返回实际 hostname/执行身份、transport、checkedAt 和基础/Docker/Trivy 独立能力状态。未授权 Docker 时不查询 Docker。基础任务检查不查询 Docker 或 Trivy；能力检查不生成目录或写入快照。
- `GET /collections/script?scope=basic|container-inventory`：分别下载 Linux Node.js 脚本，在目标机本地执行，输出 ys-host/1。目标需 Node.js；目录额外需 Docker 访问，不需 Trivy。其他平台明确拒绝。
- `POST /collections/upload`：可选 scope 校验选定任务与生成包范围，保留原始产物；旧调用不带 scope 仍兼容。目录来源是操作员上传并确认，不升级为在线验证。
- `GET /collections/snapshots?scope=...`：服务端按类型分页筛选；旧快照按原有观测推断展示类型，不改写原始资料。
- 静态 local 连接可省略 SSH 字段；部署端仍须显式绑定 customerId/assetId，网页不能为任意资产创建本机执行通道。SSH 的必填约束保持。
- 从固定目录进入容器镜像页，在导航中保留主机、snapshot 和 profile；刷新继续回读同一目录，不自动发现新目录或发起扫描。离线目录缺少在线授权时提示离线镜像生成途径。
