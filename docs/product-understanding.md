# 产品共识与待定问题

本文记录讨论中已确认的产品方向，不代表完成了实现方案或技术选型。

## 已确认

- 系统以资产管理为基础，进行 CVE 和 EOS/EOL 风险评估并生成报告。
- 项目包含前端与后端，后端需要支持调用 Pi Agent。
- 项目按业务功能模块组织代码，模块划分需方便扩展和修改。
- AI 的主要职责有两项：生成报告、调用工具。
- 工具调用采用 skills 配合固定脚本，以约束执行过程并提高准确度；输入数据和判定规则的可靠性仍需分别验证。
- 资产导入支持人工录入、脚本采集，以及 Trivy 等工具提供的数据。
- 软件通过上传 SBOM 等资料接入，由 Trivy 解析并进行漏洞评估；容器采用类似的资料接入与评估流程，具体输入形式尚待确定。
- 业务数据按客户组织，客户是资产、导入资料、评估任务和报告的归属维度；访问权限与客户登录方式尚待确定。
- 系统需要 Dashboard 展示业务信息，具体指标、统计范围与口径尚待确定。
- 用户要求技术栈尽量统一，提出 Node.js 作为方向；Dashboard 参考 Dependency-Track 等成熟产品的设计理念。
- 固定功能通过功能页面操作；对话主要用于问题解析、排查和临时工具调用、查询，例如查询近期 PHP CVE。
- 数据量大、来源格式多，资产导入需要保留灵活性。统一数据要求聚焦核心字段及其业务含义，并允许来源特有信息存在；具体字段范围尚待确认。
- 报告内容需要先经过内部复核；复核针对报告表述、结构和呈现，不修改扫描或评估判定，也不包含人工改判功能。
- NetBox 是可选方案，尚未确定必须使用；选型应优先考虑复用成熟能力，避免重复建设。

## 功能组织草案

以下为根据已确认要求提出的划分，尚未确定具体框架、目录或部署方式。

| 功能模块 | 职责 |
| --- | --- |
| 客户管理 | 客户信息、业务数据归属及客户上下文 |
| 资产管理 | 资产身份、属性、关联关系和历史信息 |
| 数据导入 | 人工录入、文件、SBOM 与工具输出的解析、字段映射和校验 |
| CVE 评估 | 漏洞情报、资产适用性、修复依据和评估证据 |
| 生命周期评估 | EOS/EOL 数据来源、产品匹配和生命周期结果 |
| 报告 | 从评估结果生成草稿、内部复核、报告版本和导出 |
| Agent 任务 | 后端调用 Pi，组织 skills 与固定脚本的执行，并记录任务进度和结果 |
| Dashboard | 按明确口径汇总客户、资产、风险和任务等业务信息，指标尚待确定 |

- 前端页面和交互按功能归属组织；后端各模块在内部组织接口、业务逻辑和数据访问。
- 模块通过明确接口协作；Pi 的启动、通信和会话管理细节集中在 Agent 任务模块。
- skills 和固定脚本按实际功能归属维护，Agent 任务模块管理其调用过程。
- NetBox、Trivy 等产品的具体接入方式放在对应功能模块内，避免其数据格式扩散到全部业务代码。
- 这些功能模块不预设为独立部署的服务。
- 建议区分公开情报查询与客户资产评估：对话查到 CVE 后，只有结合具体资产资料完成评估，才形成该资产的受影响结论。临时查询如何归档、是否触发后续评估，尚待确认。

## 技术栈与 Dashboard 建议

- 新增应用代码统一使用 TypeScript，后端与任务 Worker 使用受支持的 Node.js LTS；前端采用 React + Vite，后端采用 NestJS，按业务功能组织模块。以上具体框架为推荐方案，尚未确认最终版本与依赖。
- 前端和后端共享业务契约，并保留运行时输入校验；类型声明不能替代上传资料和工具结果的校验。
- Trivy、Pi 和可复用的已有脚本通过工具接口接入，不因统一应用技术栈而重写扫描器或全部历史脚本。长任务放在 Worker 中执行，业务接口返回任务引用。
- 业务数据建议采用 PostgreSQL；NetBox 继续作为可选资产台账，具体存储、任务队列与附件存储方案待详细设计。
- Dashboard 借鉴 Dependency-Track 的组合概览、对象与组件下钻、版本分组及显式聚合范围；本项目增加客户归属、EOS/EOL、覆盖缺口、数据新鲜度和报告状态。
- Dashboard 提议以客户为第一筛选维度，从资产／应用／镜像组合进入对象、版本或快照、组件与漏洞证据；不要求为了展示而强迫所有资产进入额外的项目层级。
- 聚合展示明确版本选择、时间范围和计数单位，趋势同时展示覆盖变化。报告复核不影响风险指标；不引入人工抑制或改判来降低统计。

## 待定

- 核心字段的最小范围、缺失字段的处理方式，以及来源特有信息的保留方式。
- 统一数据契约如何区分资产信息、工具已有的漏洞发现和来源证据。
- 人工录入与工具采集发生冲突时，如何确认资产身份和属性。
- AI 生成报告时，哪些字段和结论必须由固定评估结果提供。
- 报告草稿的编辑方式、复核流程及报告修订历史的保留方式。
- 报告最终面向谁、使用场景和交付形式。
- 用户是否均为内部团队、是否提供客户登录，以及客户间的访问权限与跨客户汇总范围。
- 资产规模及平台的持续运营范围。
- 软件和容器首版支持的上传格式、SBOM 与实际资产及版本的关联方式。
- Dashboard 的最终布局、指标公式、版本聚合规则、全局与单客户权限范围。
- 对话上下文、临时查询结果的保留方式，以及对话触发正式客户评估的规则。
- 资产管理、生命周期数据和报告能力分别复用哪些现有产品或组件。
- Pi 的运行方式、会话归属、任务恢复方式，以及推荐技术栈的最终版本、任务队列和附件存储选型。
