# 导航分区与资产删除设计讨论稿

2026-11-19。状态：用户调用implement接受推荐边界；实施以docs/tickets/navigation-and-deletion为准。

用户要求实现资产删除，并将侧边栏整理为四个业务模块；参考 Dependency-Track 的资产/组件/漏洞汇总展示思路。

## 已明确的目标

1. Dashboard 位于第一入口，展示资产、CVE 和风险概况，支持查看明细。
2. 资产管理统一组织服务器、网络设备、操作系统、系统包、Docker、软件及生命周期基础资料；采集仍与评估分别记录。
3. CVE 与 EOSL 评估集中为评估入口。
4. 第四模块用户描述为“风险和软件评估”，与第三模块可能重叠，等待明确。
5. 提供资产删除能力，不能继续缺少入口。

## 待决策树

- 第四模块边界：是否定位为“风险与报告”，承接评估结果、历史比较、风险分析、报告生成及报告内部复核，而非再发起一套软件漏洞评估？
- 删除语义：YS 移除纳管但保留采集/评估/报告历史，还是同步删除 NetBox 原生对象？与本地模式分别明确。
- Dashboard 范围：“所有”是当前客户的全部资料，还是所有有权限客户的跨客户聚合？

## 推荐导航（待确认）

| 模块 | 入口及职责 |
| --- | --- |
| 总览 | Dashboard：资产、CVE分布、受影响对象、EOSL风险、覆盖范围与趋势；点击下钻 |
| 资产管理 | 资产台账、资产采集、容器/镜像、软件/项目及SBOM、生命周期基础资料；CSV/Windows等导入方式归入相应页面 |
| 安全与生命周期评估 | CVE评估（主机/软件/镜像按支持范围选择）、EOSL评估、评估任务与历史 |
| 风险与报告 | 风险结果、差异比较、风险分析对话、报告及内部复核 |

生命周期基础资料表示产品、版本、厂商及支持期限等输入；生命周期评估表示特定资产版本与这些资料匹配后的结果。软件资料与组件归资产管理，软件漏洞扫描归评估。

现有实现限制必须继续公开：Linux主机原始包清单尚无直接CVE评估适配器，真实容器组件扫描尚未接入；菜单重组不能将这些能力显示为已可用。已有报告内部复核不修改评估判定。

## 参考

Dependency-Track术语与项目聚合：https://docs.dependencytrack.org/terminology/ 、https://docs.dependencytrack.org/usage/collection-projects/ 。借鉴对象到组件及风险汇总/下钻关系，不直接把硬件和主机强行映射为软件项目。

## 本轮只读核对事实

- 当前没有资产DELETE接口或删除按钮。
- NetBox同步对消失对象将映射标为inactive，资产记录仍保留；当前台账列表尚不排除此类对象。
- 资产历史外键未配置级联删除，直接删主记录会遇到关联约束。删除功能需要明确处理历史保留、默认列表排除、再次同步是否恢复等语义。

## 已采纳边界

删除为可恢复移出YS纳管，保留历史、不删除NetBox对象；第四模块为风险与报告；Dashboard默认当前客户。任务已发布为GitHub #19–#24。
