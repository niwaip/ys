# YS：按客户组织的资产风险评估与报告平台

状态：用户显式调用 implement-spec 进入实现；规格已发布为 GitHub #1。

https://github.com/niwaip/ys/issues/1

本规格综合当前讨论与已检查的现有环境。业务要求与实现建议分别标注；待定选型不会被当作用户已经确认的决定。本规格的编写和发布不授权执行服务器验证、部署或业务代码实现。

## Problem Statement

操作人员需要为多个客户管理资产及其风险，但资产资料来源多、数据量大、格式不统一。服务器清单、人工录入、脚本采集、软件 SBOM 和容器资料包含的信息不同，难以通过一张固定字段表完整表达，也难以将工具结果稳定关联到具体客户、资产和版本。

现成扫描与情报工具可以提供部分能力，但缺少统一的业务入口、任务记录、客户归属、Dashboard 和报告流程。对话式查询能帮助分析临时问题，例如查近期 PHP CVE，却需要明确区分公开情报与客户资产实际受影响的评估结果。

操作人员希望复用成熟工具和资产管理能力，利用 Pi Agent、skills 与固定脚本进行工具调用和报告生成，并由内部人员复核报告。评估判定需要保留原始依据，报告复核不应成为人工改判入口。系统还需要按业务功能组织代码，使数据来源、工具、报告和页面能够分别扩展。

## Solution

建设一个有前端和后端的多客户资产风险工作台。客户是资产、导入资料、任务、评估结果与风险报告的业务归属维度。

固定操作通过功能页面完成，包括客户与资产管理、资料导入、软件和容器评估、CVE 与 EOS/EOL 查询、历史查看、Dashboard、报告生成及内部复核。对话用于问题解析、排查、公开情报查询和临时工具调用，由后端调用 Pi Agent，并通过 skills 配合固定脚本连接现有能力。

不同输入映射到统一核心语义，同时保留来源特有信息。软件通过 SBOM 等资料接入，由 Trivy 解析和评估；容器采用类似流程。后端同时支持直接调用 Trivy 或固定脚本，页面中的确定性操作无需强制经过一次大模型对话。

评估结果、证据和报告事实由可追溯的数据处理与工具执行产生。AI 据此生成报告草稿，内部复核调整文字、结构和呈现，正式交付时绑定所采用的数据和评估版本。NetBox 是资产管理复用方案的候选，最终采用范围需要根据功能适配和维护成本确定。

## User Stories

下列故事采用“作为某角色，我希望获得某能力，以便得到某收益”的句式。操作人员、分析人员和内部复核人员代表业务职责，具体账号、角色和客户登录方式尚待选型，不预设必须由不同的人担任。

1. 作为操作人员，我希望按客户组织业务资料，以便区分不同客户的资产和工作内容。
2. 作为操作人员，我希望查看明确的当前客户上下文，以便知道正在操作哪位客户的数据。
3. 作为操作人员，我希望在权限允许的范围内切换客户，以便管理多个客户的工作。
4. 作为操作人员，我希望资产、上传资料、任务和报告都能追溯客户归属，以便完整查看一次客户评估的来龙去脉。
5. 作为操作人员，我希望手工建立和补充资产信息，以便管理无法自动采集的对象。
6. 作为操作人员，我希望导入脚本采集得到的资产资料，以便复用现有采集方式。
7. 作为操作人员，我希望上传软件物料清单，以便识别软件组件并进行漏洞评估。
8. 作为操作人员，我希望上传容器相关资料，以便使用同一工作台管理容器风险。
9. 作为操作人员，我希望在导入时关联客户及被评估对象，以便将后续结果放到正确位置。
10. 作为操作人员，我希望预览识别出的字段和无法识别的内容，以便发现错误映射。
11. 作为操作人员，我希望不同来源只遵守必要的核心字段约束，以便接入内容差异很大的资料。
12. 作为操作人员，我希望保留来源特有的扩展信息，以便不因统一格式丢失后续可能需要的数据。
13. 作为操作人员，我希望保留原始资料和来源信息，以便复核导入结果并重新处理。
14. 作为操作人员，我希望看到缺失字段及其对评估的影响，以便有针对性地补充资料。
15. 作为操作人员，我希望有效记录与问题记录被分别说明，以便判断一批导入资料的处理情况。
16. 作为操作人员，我希望重复导入具有可解释的处理结果，以便避免无意产生重复资产和重复评估。
17. 作为操作人员，我希望同名但不同客户的资产保持独立，以便避免结果串联。
18. 作为操作人员，我希望看到同一对象的资料采集时间与导入时间，以便判断其时效性。
19. 作为分析人员，我希望区分软件应用、软件组件和容器镜像的关系，以便将漏洞关联到正确对象。
20. 作为分析人员，我希望将 SBOM 关联到具体对象及版本，以便知道评估依据对应哪个状态。
21. 作为操作人员，我希望从功能页面发起 Trivy 评估，以便快速执行固定工作流程。
22. 作为操作人员，我希望通过固定脚本完成已有工具支持的操作，以便复用成熟能力。
23. 作为操作人员，我希望查看任务状态、进度和错误原因，以便判断工作是否完成。
24. 作为操作人员，我希望页面断开后仍能重新查看任务结果，以便不依赖浏览器持续在线。
25. 作为操作人员，我希望重复提交和执行超时具有明确语义，以便避免重复任务或误报成功。
26. 作为分析人员，我希望查看一次评估的输入、工具版本、执行时间与情报库时间，以便重现结论。
27. 作为分析人员，我希望区分漏洞严重程度、资产适用性和证据充分程度，以便正确理解风险。
28. 作为分析人员，我希望看到受影响组件、安装版本、受影响范围和已取得的修复依据，以便安排处理。
29. 作为分析人员，我希望来源缺失、工具失败、未扫描和没有发现分别呈现，以便不把覆盖缺口理解为安全。
30. 作为分析人员，我希望过期漏洞库和缓存结果被明确标注，以便判断评估的新鲜度。
31. 作为分析人员，我希望未知版本、未知日期和未知判定保持其原义，以便避免产生没有依据的结论。
32. 作为分析人员，我希望软件和操作系统使用适合各自来源的版本及补丁判断，以便减少错误匹配。
33. 作为分析人员，我希望查看某个漏洞发现的证据和数据来源，以便理解其判定依据。
34. 作为分析人员，我希望历史评估可以独立查看，以便比较不同时间的结果。
35. 作为分析人员，我希望查询产品的 EOS/EOL 状态，以便识别生命周期风险。
36. 作为分析人员，我希望生命周期日期附带阶段含义、来源及匹配依据，以便区分不同厂商的公告语义。
37. 作为分析人员，我希望生命周期数据缺失或匹配不足时明确显示未知，以便决定需要补充哪些资料。
38. 作为分析人员，我希望分别查看 CVE 风险和生命周期风险，以便采取各自适用的处理措施。
39. 作为操作人员，我希望在 Dashboard 查看所选客户的资产和风险概况，以便快速了解当前情况。
40. 作为分析人员，我希望 Dashboard 的统计口径可追溯，以便理解数字对应哪些资产和评估记录。
41. 作为分析人员，我希望 Dashboard 同时说明评估覆盖与数据新鲜度，以便发现尚未完成的工作。
42. 作为操作人员，我希望从 Dashboard 进入相关明细，以便追查某个数字或风险项。
43. 作为分析人员，我希望通过对话查询近期 PHP CVE，以便处理临时的情报需求。
44. 作为分析人员，我希望通过对话解释漏洞条件、来源和修复资料，以便分析具体问题。
45. 作为分析人员，我希望 Pi 能调用已有 skills 和固定脚本，以便完成工具支持的临时工作。
46. 作为分析人员，我希望对话中的工具执行显示任务状态和来源，以便确认实际执行了什么。
47. 作为分析人员，我希望公开情报查询与客户资产评估具有明确区别，以便避免将搜索结果误当作客户漏洞。
48. 作为分析人员，我希望涉及客户资料的对话使用正确的客户上下文，以便保护不同客户的数据归属。
49. 作为分析人员，我希望在资料或来源不足时得到明确的缺口说明，以便补充后继续分析。
50. 作为报告编制人员，我希望按选定客户和评估范围生成报告草稿，以便减少整理工作。
51. 作为报告编制人员，我希望 AI 基于已有结果组织摘要和解释，以便提高报告的可读性。
52. 作为报告编制人员，我希望报告中的统计、标识符、版本与日期可追溯到评估资料，以便核查事实。
53. 作为内部复核人员，我希望调整报告文字、结构和呈现，以便满足交付需要。
54. 作为内部复核人员，我希望复核不改变评估判定，以便保持报告与原始结果一致。
55. 作为内部复核人员，我希望看到报告修订与复核状态，以便知道哪些内容已经检查。
56. 作为报告编制人员，我希望交付的报告绑定所采用的资料与评估版本，以便后续说明其依据。
57. 作为报告编制人员，我希望导出经过内部复核的报告，以便交付给实际使用者。
58. 作为维护人员，我希望导入、评估、报告和 Pi 接入按功能模块组织，以便独立修改。
59. 作为维护人员，我希望增加工具或输入格式时复用已有业务契约，以便控制改动范围。
60. 作为维护人员，我希望复用适合的资产台账、扫描器和报告能力，以便减少重复建设。

## Implementation Decisions

### 已确认的架构约束

- 前端承载固定功能页面、Dashboard 和对话交互；后端承载业务数据、评估任务及 Pi 调用。
- 按功能模块组织前后端。建议的模块为客户管理、资产管理、数据导入、CVE 评估、生命周期评估、报告、Agent 任务和 Dashboard。具体模块命名可在设计中调整。
- 模块公开其业务接口，在内部组织数据访问与实现。工具输出格式和 Pi 通信细节由相应模块处理，不扩散为所有页面必须了解的内容。
- 后端同时支持直接调用 Trivy／固定脚本，以及由 Pi 经 skills 调用工具。固定页面操作与对话调用复用相同业务契约。
- AI 的两个主要职责是报告生成和工具调用。固定脚本负责可重复执行与结构化输出，但仍需验证输入、产品匹配及来源质量。
- 报告内部复核不修改评估判定，不实现人工覆盖漏洞或生命周期判定的功能。
- 优先复用现成能力，NetBox 的采用与接入范围保持待定。功能模块划分不要求分别部署，也不预设微服务架构。
- 技术栈应尽量统一，用户提出 Node.js 作为方向；Dashboard 应参考 Dependency-Track 等成熟产品的设计理念。

### 技术栈推荐方案：待最终确认

- 新增前端、后端、任务 Worker 和工具编排代码统一采用 TypeScript。浏览器运行前端构建产物，后端与 Worker 使用受支持的 Node.js LTS；初始设计以既有环境中的 Node.js 24 LTS 为兼容基线，实施时锁定受支持的安全补丁版本。
- 前端建议 React + Vite，后端建议 NestJS，前后端均按业务功能模块组织。NestJS 的功能模块封装对应业务的接口与实现，而非在整个项目中只按控制器、业务逻辑、数据访问进行全局分组。
- 共享稳定业务类型、状态及校验契约；上传资料、工具输出和网络请求仍经过运行时校验。避免将后端数据访问对象或工具原始结构直接暴露给所有前端功能。
- Node.js Worker 承担评估、报告和 Pi 任务，业务接口提交任务并返回引用。异步调用 Pi、Trivy 和已有固定脚本，采集结构化结果、退出状态及标准错误，管理超时和取消；不在普通请求中同步等待长扫描。
- 新增编排与归一化逻辑优先使用 TypeScript。可复用的 Python 脚本、扫描器和可选 NetBox 保持外部工具或系统角色，通过明确契约接入；统一技术栈不要求重写这些能力。
- 业务存储建议 PostgreSQL，扩展属性及原始资料的结构化元数据与核心关系分别管理。具体数据库访问库、任务队列、附件存储和组件库保持待选，不在本次规格阶段安装依赖。

### 数据契约建议：核心稳定，扩展开放

- 客户归属、输入来源、导入记录、评估对象和处理状态具有统一语义。具体字段名及必填规则由详细设计确定，当前不冻结完整 Schema。
- 系统内部编号与来源提供的身份分别保存。资产身份需要考虑客户、对象类型和来源标识；主机名、IP、软件名或镜像标签不能单独作为所有对象的全局身份。
- 导入资料保留来源名称、原始资料引用、内容校验信息和导入时间；采集时间已知时单独记录，未知时不以导入时间冒充。
- 标准字段之外允许来源特有的扩展数据。原始资料、扩展属性和归一化信息之间保持可追溯关系；扩展信息不直接绕过核心校验。
- 软件应用、组件、容器镜像与运行实例是可能不同的业务对象。SBOM 描述的组件关系需关联到评估对象与对应版本；镜像内发现不能自动证明某个运行实例采用了该镜像。
- 软件版本、包生态、发行版信息、PURL、CPE、厂商和型号等按来源与评估需要保留。未知信息可以接入，但必须说明因此无法执行或确认的评估范围。
- 客户资产信息、工具产生的漏洞发现和原始证据分别表达。工具返回一个 CVE 不直接转为对任意同名客户资产的受影响结论。
- 支持逐条说明处理结果。不能解析或无法关联的记录应得到明确错误或待补充状态；是否允许同批部分提交及其事务规则由接口设计明确。
- 同一输入的重复接入、同一任务的重复提交以及同一对象的多次评估分别定义去重或幂等语义，保留必要的历史。

### 评估与历史建议

- 一次评估绑定明确输入版本、工具及规则版本、执行范围、执行时间、情报库或资料时间、结果与证据。后续数据更新不静默改写该次历史。
- 工具执行状态、数据覆盖状态、漏洞严重程度和资产适用性分别表达；结果非空不证明覆盖完整，工具返回成功也不证明输入足够。
- 对库过期、来源不可用、输入版本缺失、工具不支持和部分失败进行结构化披露。未查询、未知、无发现与已确认不受影响保持不同语义。
- 软件及容器路径优先复用 Trivy 对所支持资料的解析和漏洞评估能力。首版具体支持哪些 SBOM 格式、镜像资料及脚本输出，需要依据实际接口确定并公开支持清单。
- 不根据 KB 数字大小推断补丁替代关系，不将跨发行版的上游版本比较直接当作最终补丁状态；与 Windows 有关的旧规则需要逐项验证后复用。
- 生命周期结果保留产品匹配、阶段名称、日期、来源和核实状态；不同厂商的生命周期阶段不得只靠相同缩写合并。未知日期保持未知。
- 软件与容器漏洞评估不自动提供 EOS/EOL 数据；生命周期能力需要独立资料来源和匹配逻辑。
- 新扫描与历史记录同时可查。资产归档或删除时如何保留关联身份及清理历史，应在数据生命周期设计中明确，避免业务删除意外抹去报告依据。

### Agent 任务与对话建议

- Agent 任务模块统一管理 Pi 的启动或连接、会话、任务提交、进度、错误和结果。具体进程模型、RPC 方式和恢复机制保持待定。
- 后端保存任务状态和结果，前端可重新查询；浏览器连接不承担唯一的任务生命周期管理职责。
- 任务契约至少表达业务范围、客户上下文、输入引用、所用能力、执行状态、错误和结果引用；固定脚本对结构化输入输出、退出状态和超时语义作出明确约定。
- 面向用户的操作可先采用等待、执行中、成功、部分完成、失败及取消等候选状态；实际状态机及重复提交处理在接口设计时确认。
- Pi 调用工具时，通过与功能页面相同的后端规则校验客户归属和允许操作范围。客户权限不能仅由对话提示词保证。
- skills 描述适用场景和执行流程，固定脚本或工具接口完成具体操作。新增能力需要声明输入、输出和失败行为。
- 对话可独立查询公开情报。查询近期 PHP CVE时，记录产品范围、时间条件、来源、查询时间及覆盖缺口，不能将工具调用失败替换为模型记忆中的“最新结果”。
- 当对话需要使用客户资料或执行客户评估时，明确使用该客户上下文。是否自动将查询升级为正式评估、临时结果如何归档，仍是待确认规则。
- 对话记录、工具执行记录和正式评估记录通过引用关联，保持各自业务含义。

### Dashboard 与报告建议

- Dashboard 支持所选客户的业务汇总和明细跳转。跨客户汇总是否提供、谁能查看，由权限与使用范围决定。
- 参考 Dependency-Track 的组合、项目、组件与漏洞视角，以及按版本或标签明确聚合范围的设计。YS 的客户归属、EOS/EOL、覆盖缺口和报告状态是本项目补充，不视为参考产品已经提供的同等能力。
- 建议下钻关系为客户、资产／应用／镜像组合、具体对象与版本或快照、组件及漏洞、来源证据。项目分组为可选导航组织，不强制为每类资产增加项目实体。
- Dashboard 建议包含资产与组件、CVE 严重程度分布、受影响对象、EOS/EOL 状态、评估覆盖与资料新鲜度、任务及报告状态，并提供风险排序和明细入口。
- 版本筛选和趋势明确采用的输入与评估快照；当前视图优先采用当前纳管对象的选定版本或快照，历史记录可单独查询。风险数下降时同时展示覆盖变化，避免因对象退出范围或扫描失败造成错误解释。
- 不直接采用参考产品的风险分数公式。若后续增加综合评分，需要明确其输入、权重、适用性与未评估范围，禁止由 AI 临时生成指标。
- Dependency-Track 的人工分诊和抑制流程不是本项目的报告复核流程；报告编辑与复核不改变原始判定或减少风险统计。
- 建议的初始展示包括资产及组件数量、已评估与未评估范围、CVE 严重程度及适用性、生命周期风险、任务状态和数据更新时间，最终指标待界面设计确认。
- 统计应明确数据范围、采用的评估版本和去重方式。历史扫描行数、唯一 CVE 数、资产漏洞实例数和确认受影响资产数不可混为同一数字；部分覆盖不得显示成完整安全结论。
- 报告生成读取已选择的数据与评估结果。AI 负责摘要、组织、解释和建议；CVE 标识、判定、数字、版本和日期由可追溯的事实输入提供并校验。
- 报告复核编辑叙述与呈现；承载判定和统计等事实的内容通过受控呈现或发布校验保持与评估结果一致。发现输入问题时返回资料或评估流程处理，不在报告复核中改判。
- 建议的报告流程为草稿、待复核、复核通过、正式交付；修改已通过的报告应形成新修订并重新复核。角色权限和具体流转细节待确认。
- 报告至少需要可预览和可交付输出，具体采用 HTML、Word、Excel 或 PDF 等哪些格式尚未决定。报告包括生成依据、范围、评估时间和必要的覆盖缺口说明。

### 接口及存储设计范围

- 后端应提供客户与资产管理、导入预览和提交、发起与查询评估、读取结果与证据、报告生成和复核交付、Dashboard 查询、对话任务提交与进度读取等业务接口。
- 列表查询需要明确客户范围、分页和筛选语义；大型证据或附件按需加载。非法或无权限的客户／对象引用不得退化成不受限查询。
- 数据模型需涵盖客户、评估对象及关联、软件组件、导入批次与资料版本、任务、评估记录、发现与证据、生命周期记录、对话引用、报告修订与内部复核记录。
- 当前推荐 TypeScript、Node.js LTS、React + Vite、NestJS 与 PostgreSQL；具体依赖版本、队列和附件存储仍待详细设计。NetBox 是否承担资产主数据，以及其与平台业务数据的关系，需要明确权威来源、身份映射和同步规则。

## Testing Decisions

### 主验收边界草案：待用户确认

优先在后端向前端公开的业务接口处验证整条工作流：在指定客户下导入资料，完成归一化和评估，查询任务、结果及 Dashboard，生成并内部复核报告，再取得交付输出。该边界同时覆盖页面与对话共享的业务规则，避免围绕每个内部类或函数建立重复的验收面。

少量浏览器端到端测试验证客户切换、关键页面交互、任务进度呈现和报告复核。对进程或工具接入需要的测试使用其真实输入输出契约，范围限于主接口测试不能充分表达的失败和兼容行为。

### 好测试的标准

- 验证用户可观察结果、数据归属、状态和报告事实，不固定内部类名、方法调用顺序、目录或具体实现方式。
- 正常路径之外，重点覆盖跨客户引用、身份歧义、版本缺失、部分失败、过期库、超时、重复提交和报告事实偏移。
- 默认使用固定资料、固定工具输出和可替代的 Pi 进程／情报来源，使自动验收可重复；测试失败不能依赖在线 API 当时是否可用。
- 真工具兼容验证使用标明性质的样例和隔离环境，另外记录版本及库时间。必须在获得明确执行指令后开展，规格发布本身不触发验证。

### 模块与场景

1. 客户及权限：同名资产在不同客户下不串联；通过对象编号、结果引用或对话工具调用均不能取得无权限客户的数据。
2. 导入：人工、脚本资料和 SBOM 映射到一致核心语义；扩展信息可查，原始资料可追溯；坏记录和缺失字段得到明确处理结果。
3. 软件及容器：评估输入关联正确对象与版本；Trivy 解析结果保留组件、生态、安装版本、发现和来源，无法评估的范围被披露。
4. CVE：严重程度和适用性分别展示；无版本、补丁证据不足、库过期和引擎失败不能表现为“已修复”或“没有漏洞”。
5. 生命周期：日期阶段与来源可查；部分无效日期不抹去同记录有效信息；未匹配或缺失日期保持未知。
6. 任务：开始、部分完成、失败、超时和重复请求返回可解释状态；页面重连能读取任务及结果，历史评估不会被新任务静默覆盖。
7. Pi：功能页面和对话共享客户与输入校验；固定脚本收到约定输入，错误或非预期输出被明确处理；普通情报查询不直接产生客户受影响结论。
8. Dashboard：统计可对应到选定客户、对象版本和时间范围内的明细，不重复累加历史扫描；覆盖缺口和数据时间可见；切换版本、快照和筛选条件后指标与下钻结果一致，报告复核不改变风险统计。
9. 报告：AI 草稿的标识、数字、版本、日期与判定能对应事实输入；内部复核不能改变评估结果；修改通过后的报告会形成需要复核的新修订。
10. 扩展：增加一种输入解析或替换一种工具实现后，共享业务接口的既有验收仍通过，用户不必适应另一套客户、任务和结果语义。

### 现有先例与限制

当前项目仓库只有讨论文档及探索产物，尚无业务实现或可沿用的项目测试接口。主验收边界属于新提议。

旧 YATA 文档中的快照过滤、原子保存、幂等、保存回读、历史保留、覆盖缺口、坏日期降级和报告事实校验，可以作为场景先例；旧测试源码没有包含在已提供的源码包中，文档宣称的测试结果不能当作本项目已经通过的测试。

## Out of Scope

- 本规格阶段不实现业务代码，不部署前后台，不安装或更新主机工具，不执行服务器验证或客户扫描。后续实施及验证需得到明确指令。
- 不承诺完整照搬旧 YATA、保持旧界面或原样复用其部署方式。
- 不强制采用 NetBox 或旧 Streamlit 架构，也不预设微服务拆分；技术栈按统一 Node.js／TypeScript 方向提出框架建议，最终版本仍待确定。
- 不实现通过报告内部复核修改漏洞、修复状态或生命周期判定的能力。
- 不将公开 CVE 查询、软件名称关键词命中或工具成功退出当作客户实际受影响的充分依据。
- 不承诺 Trivy 覆盖任意软件、任意输入格式，或自动提供所有产品的生命周期资料。
- 不承诺通过旧源码包恢复历史业务数据、测试套件、采集器、密钥或 EOS 主数据。
- 客户自助门户、主动网络／DAST 扫描、PoC 执行、自动修改客户主机、整改工单、持续监控和定时扫描，尚未纳入确认范围；需要独立确定需求与执行规则。

## Further Notes

### 已知基础

- 项目 issue tracker 已由用户指定为 GitHub 的 niwaip/ys，远程仓库已配置，Issues 可用。
- 最近一次环境检查发现主机上已有 NetBox 基础栈、Pi Agent、Trivy、Nuclei、Xolotl 与 CVE 查询技能；当时 NetBox 没有客户资产数据，且未安装旧 YATA 插件。
- Pi Web UI 使用独立实验配置，不能据此认为它已接入主 Pi 的所有技能与业务数据。主机上组件存在也不代表本项目的集成验收已完成。
- 旧 YATA 提供业务语义与历史缺陷参考；源码包和重建指南之间存在部分缺项及描述差异，复用前需做针对性审查。
- 此前探索产生的工具结果只说明相应样例的执行情况，不能证明产品、客户流程、EOS/EOL、AI 报告或整体部署已完成验证。

### 未决事项及处理方式

- 内部多客户工作台是当前设计建议；是否支持客户直接登录、客户间权限及跨客户视图尚待决定。
- 核心字段、身份冲突策略、资产类型范围、输入支持清单以及 SBOM 与真实对象的关联规则需要在详细设计中明确。
- 生命周期主数据来源、更新机制、产品覆盖范围及与软件／容器评估的关系需要单独设计。
- 对话是否可直接触发正式客户评估、会话与临时查询如何保留，以及长任务恢复方式尚待决定。
- 报告受众、模板、交付格式、复核操作和修订保留规则需要形成具体设计。
- 数据规模与性能目标尚未给定，不能用旧系统的少量资产或单次样例耗时作为容量承诺。
- 技术栈已提出统一 Node.js／TypeScript 的推荐方案；具体版本、NetBox 复用范围、队列及附件存储需要进一步形成可评审决定。上述建议不能被实现者静默当作用户已经确认的全部选择。
