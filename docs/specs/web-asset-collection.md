# YS：网页多入口资产采集与分层资料管理

日期：2026-11-19。状态：已发布为 [GitHub #18](https://github.com/niwaip/ys/issues/18)，标签ready-for-agent；不是实现、SSH执行或扫描指令。本规格扩展既有资产风险平台，不将原T01–T15的本地实现验收视为本功能已存在。

## Problem Statement

操作人员需要从网页为客户建立可靠的资产基础数据：有些资料可以手工提供，有些来自采集脚本，还有些希望直接让后台Pi Agent连接目标获取。当前系统虽有资产台账、部分导入和软件/镜像SBOM评估，但缺少贯通三种入口的Linux主机采集流程及主机关联。

目标机可能只有普通SSH账号，没有Trivy。若要求先安装扫描器，基础OS、系统包和软件版本等原本可直接查询的资料就无法进入系统。另一方面，基础主机资料、Docker引擎版本、容器内部组件和应用依赖又容易混为一谈，导致一次基础采集被误解成已经扫描全部容器和软件，或将未取得数据显示成空清单和无风险。

操作人员需要根据实际取得内容分层保存资料，明确来源、权限、对象和历史版本，再独立选择资料执行风险评估。

## Solution

在客户工作空间提供统一“资产采集”功能，支持手动输入、上传脚本采集结果、调用后台Pi Agent三种入口。操作人员无需切换到独立Pi终端；网页可查看任务进度、单项结果、缺口及保存后的采集快照。

基础采集直接使用目标机已有的受控查询命令，取得OS、运行内核、架构、可见硬件/网络信息、系统包清单及可直接确定的软件版本。SSH执行方式不要求目标机安装Trivy，也不自动安装、提权或修改目标配置。普通账号只能取得其权限允许的信息；不可读、不支持和执行失败分别披露。

Docker引擎自身属于软件版本资料；容器、镜像及内部组件作为独立范围，单独发起获取或上传镜像SBOM。软件应用的组件通过软件SBOM提供，不因基础采集而自动遍历应用目录。三入口共享客户归属、核心校验、来源、快照和幂等规则，但保留各类原始资料与扩展。

采集负责基础数据，风险评估引用明确输入版本，独立保存任务、结果与证据。采集成功不表示已评估，也不表示完整覆盖或无风险。

## User Stories

1. 作为操作人员，我希望在网页看到资产采集入口，以便不依赖独立终端完成常规工作。
2. 作为操作人员，我希望看到当前客户，以便将资料归入正确客户。
3. 作为操作人员，我希望选择已登记的目标资产，以便将采集结果关联到明确对象。
4. 作为操作人员，我希望复用现有手工建档能力登记新主机，以便为尚无资料的主机发起采集。
5. 作为操作人员，我希望选择手动输入、上传或Pi采集，以便使用手头已有条件。
6. 作为操作人员，我希望直接填写可知的主机资料，以便管理不能连接的目标。
7. 作为操作人员，我希望为手工资料标注来源和已知时间，以便不将人工声明误作自动采集证据。
8. 作为操作人员，我希望上传脚本结果，以便复用现场或客户提供的采集方式。
9. 作为操作人员，我希望查看识别出的字段与扩展，以便发现格式或映射错误。
10. 作为操作人员，我希望不能识别的格式明确提示不支持，以便补充正确资料而不是得到虚假成功。
11. 作为操作人员，我希望保留原始资料和内容校验信息，以便追溯归一化结果。
12. 作为操作人员，我希望在网页输入采集需求并调用后台Pi，以便直接获取所选目标资料。
13. 作为操作人员，我希望自然语言需求与所选客户、目标和能力范围共同约束任务，以便避免目标理解错误。
14. 作为操作人员，我希望选择已配置的连接引用，以便不在问题描述中填写密钥或口令。
15. 作为操作人员，我希望Pi调用固定skill与采集工具，以便取得可校验的实际执行结果。
16. 作为操作人员，我希望Pi不可用时明确看到原因，以便改用手工或上传入口。
17. 作为操作人员，我希望仅有SSH和系统查询工具时也能采集基础资料，以便不必先安装Trivy。
18. 作为操作人员，我希望使用普通账号取得有权限读取的资料，以便在有限权限环境开展资产管理。
19. 作为操作人员，我希望采集不会自动提权、安装或修改主机，以便符合基础信息获取的范围。
20. 作为操作人员，我希望区分连接失败、主机身份校验失败、命令缺失和读取权限不足，以便采取正确处理方式。
21. 作为操作人员，我希望取得OS发行版、版本和架构，以便识别主机平台。
22. 作为操作人员，我希望运行内核与已安装内核包分别表达，以便避免版本混淆。
23. 作为操作人员，我希望取得账号可见的CPU、内存、磁盘和网络信息，以便补充主机基础资料。
24. 作为分析人员，我希望系统包记录名称、完整版本、架构及安装状态，以便保留后续匹配依据。
25. 作为分析人员，我希望包查询保留发行版及原始版本语义，以便不丢失epoch、release或厂商修订信息。
26. 作为分析人员，我希望已卸载残留配置、未完整安装和已安装状态被区分，以便不错误统计已安装软件。
27. 作为分析人员，我希望系统包清单与手工安装软件、应用依赖的覆盖分别说明，以便不将其当作全部软件。
28. 作为分析人员，我希望基础采集能保存直接取得的Docker版本，以便管理主机软件。
29. 作为分析人员，我希望区分Docker客户端、已安装引擎包和实际运行引擎版本，以便不使用错误替代值。
30. 作为操作人员，我希望无法访问Docker daemon时仍保留其他基础结果，以便部分权限不足不导致全部资料丢失。
31. 作为操作人员，我希望通过独立操作获取容器资料，以便控制采集范围和必要权限。
32. 作为操作人员，我希望查看实际容器与镜像关联，以便知道哪些组件资料属于哪个运行对象。
33. 作为分析人员，我希望容器ID、镜像ImageID、manifest digest及标签分别保存，以便避免身份混淆。
34. 作为分析人员，我希望镜像组件只关联明确镜像输入，以便不把镜像结果直接当作整台主机或容器可写层的事实。
35. 作为操作人员，我希望容器内部资料不可得时可以另行提供镜像SBOM，以便继续后续工作。
36. 作为操作人员，我希望上传软件SBOM并关联明确的软件对象与输入版本，以便分析应用组件。
37. 作为分析人员，我希望软件SBOM不会仅凭同名自动绑定主机部署，以便避免无来源关联。
38. 作为操作人员，我希望基础采集不会默认扫描应用目录或全部镜像，以便保持各层次的执行边界。
39. 作为操作人员，我希望查看持久任务状态和已完成步骤，以便知道Pi与固定工具实际执行到了哪里。
40. 作为操作人员，我希望刷新或重新登录后还能查看任务，以便不依赖浏览器持续在线。
41. 作为操作人员，我希望重复提交可回读同一任务，以便避免重复采集。
42. 作为操作人员，我希望超时、中断和重试具有明确含义，以便不将未知执行状态误作成功。
43. 作为分析人员，我希望各项资料分别标记已取得、未采集、不支持或失败，以便理解覆盖范围。
44. 作为分析人员，我希望未知值、缺失清单和明确空清单保持区别，以便不把缺口解释为零对象。
45. 作为分析人员，我希望每次采集形成不可变快照，以便回看主机在不同时间提供的资料。
46. 作为分析人员，我希望采集时间、导入时间、工具版本和来源分别保留，以便判断资料时效性。
47. 作为操作人员，我希望重复上传有可解释的去重结果，以便不无意制造重复资产。
48. 作为操作人员，我希望同名、同IP但属于不同客户的主机保持独立，以便避免资料串联。
49. 作为操作人员，我希望身份矛盾时资料得到明确处理，以便不悄悄绑定到错误主机。
50. 作为分析人员，我希望选择已有资料版本再发起评估，以便明确评估采用的依据。
51. 作为分析人员，我希望基础采集完成后仍标记未评估，以便区分资料取得和风险判断。
52. 作为分析人员，我希望不受支持的输入明确显示暂不可评估，以便不将采集失败或引擎缺失解释为安全。
53. 作为分析人员，我希望更新评估依据后能复用旧采集资料，以便不强制重新连接主机。
54. 作为报告编制人员，我希望评估及报告能追溯其采集快照和原始来源，以便核实结论。
55. 作为维护人员，我希望增加输入适配器或采集执行方式时复用业务契约，以便避免新增孤立的数据流程。
56. 作为操作人员，我希望HTTP部署下所有入口和菜单均可使用，以便不再因浏览器环境差异出现整页空白。

## Implementation Decisions

### 已确认的业务边界

- 网页是主要交互入口，支持手动输入、上传脚本结果、后台Pi采集；不要求操作人员转到独立Pi终端。
- 以客户、明确目标及资料版本组织数据。采集入口和执行方式分别表达，Pi入口可以调用本地或SSH执行器；上传入口不要求目标在线。
- 基础采集取得直接信息；Docker软件版本与容器内部组件分层；软件组件通过SBOM接入。基础采集不默认进入容器内容、应用目录或漏洞扫描。
- 采集与风险评估分离；不会因为采集完成自动建立受影响结论，也不会让报告复核改变原始判定。
- 新增能力沿用TypeScript、Node.js、React和NestJS按功能组织的现有架构，不另建孤立台账或强制引入NetBox。

### 模块与公开业务接口

- 新增资产采集功能，公开提交手工资料、上传资料、提交Pi任务、列出/读取任务、读取快照及原始来源的客户范围业务接口。沿用现有身份校验、参数化持久化、分页和事务边界。
- 目标资产复用现有台账；首片可先在既有资产页面建档后返回选择，不要求另造复杂目标发现向导。
- 采集模块封装任务与快照；输入适配器封装格式解析；执行器封装本地/SSH；Pi能力只负责调用经授权的固定工具。评估模块通过公开读取契约取得快照，不直接依赖采集器内部输出。
- 连接配置使用服务端受控的目标地址、端口、账号、认证材料引用及可信主机身份。操作员选择有权使用的配置；首片允许运维预配置，不要求实现通用凭据库或密钥分发产品。
- 请求只接收必要业务输入与幂等标识。客户、目标、连接和来源归属由服务端逐项校验，不由Pi提示词保证。自然语言不提供任意地址、路径或命令以绕过固定范围。

### SSH与基础采集的保守实施默认值

- 用户已明确基础采集不依赖Trivy；据只读账号使用场景，本规格采用固定查询、不自动安装、不自动提权、不修改目标配置的默认值。此默认值是实施约束，不声称用户已批准某台主机或某账号执行。
- SSH负责连接并运行版本化固定采集命令/协议。不会将模型生成的shell作为可执行输入；设置连接/执行超时、输出上限和明确退出语义。禁止关闭主机身份验证或自动接受不可信身份变化。
- “只读账号”是部署权限与执行约束的组合，不能仅凭账号名称推断；读取范围以实际授权为准。无权限、不支持和查询失败分别披露，不自动尝试sudo或改变用户组。
- OS与包查询按明确支持的Linux发行版/包管理器适配。首个支持清单必须覆盖用于验收的YS主机发行版并在实施中固定；其他平台返回不支持或部分覆盖，不能根据包名猜产品。
- 直接读取发行版信息、运行内核和可见系统信息；包查询保留名称、原始完整版本、架构、安装状态、包管理器与查询范围。主机硬件不可见或包查询受限不回填虚构值。
- Docker版本分别记录客户端版本、安装包声明的引擎版本与可验证的运行引擎版本。只有客户端可读时，运行引擎版本保持未知。查询daemon前校验配置范围，不自动加入docker组或将其视为只读授权。
- 基础采集不把源端没有Trivy记为整次失败；只有选择依赖Trivy的独立能力时，才报告该能力不可用。

### 输入、快照与身份

- 三入口统一必要核心语义：客户、目标资产、来源类型/版本、采集范围、资料/任务引用、可知采集时间、接入时间、处理状态及缺口。各输入保留扩展，不冻结一张承载所有资料的宽表。
- 手工输入保存人工来源；上传资料经版本化适配器处理，保留原文及哈希。不接受模型猜测映射为已经核实的事实；未知格式/版本保留明确不支持结果，不建立虚假可评估快照。
- 每次有效内容生成固定快照及分项资料引用；后续采集不改写旧快照或已有评估。输入资料、归一化记录与对象关联在同一事务中提交；失败不留下半份成功快照。
- 显式目标资产编号是关联上下文，不能以主机名/IP替代。来源身份变化或与目标矛盾时保留待解决状态，不自动覆盖已绑定目标；具体身份字段由适配器说明。
- 重复任务按客户范围幂等键及完整输入复用；同键不同目标/范围/连接冲突。重复上传按来源格式、内容哈希和目标关联校验；不能把同内容跨对象重绑静默当成功。
- 缺失清单、明确空清单、部分结果分别表示；分项状态包含已取得、未采集、不支持、权限不足、失败等语义。未知时间不以导入时间冒充采集时间。
- 对大包清单和SBOM使用明确大小/项数限制、分块/附件及分页读取策略；不得沿用原有500KB/1000组件限制后静默截断。实施需给出可重复边界测试，超限明确拒绝或完整分批接入，不承诺无限规模。

### Pi任务与页面交互

- 复用现有Pi RPC、独立会话、固定工具、进程期限和输出校验能力，新增客户范围采集skill和固定工具；不修改现有公开情报或只读风险对话的业务含义。
- Pi只取得当前任务所需的已授权目标描述和能力目录；后台工具持有连接引用并执行。密钥/口令不进入模型输入、任务响应或事件；原始输出也需限制字段与敏感内容。
- 工具输出独立校验任务、客户、目标、范围、产物路径及结果结构。Pi的自由文字不作为OS、包、版本或采集成功的依据；模型完成也不等于工具完成。
- 网页提供三入口、范围说明、状态、结果预览和来源详情。上传/手工资料通过校验后保存基础数据，不引入对评估判定的人工改判；字段纠错通过新资料版本实现。
- 任务持久保存排队、执行、成功、部分完成、失败、不可用、超时及中断语义；刷新可回读，详情按需加载。复用单后端worker假设，不引入分布式调度系统。
- 运行中任务重启后标记中断，不盲目重连重采；排队任务在重新核验授权及连接配置后恢复。终态任务主动重试使用新请求，保留历史。
- 页面在实际HTTP条件下可用，导航往返、客户切换、请求取消及任务轮询不会使整页内容消失或保留前一客户资料。

### 容器、软件与评估交接

- 容器资料作为独立操作，明确选择目标及所需能力；基础采集默认只取Docker软件版本，不连带读取容器/镜像目录和内部内容。后续允许将目录读取与内部组件获取分别声明，但不隐式扩大范围。
- 独立容器资料可包含实例/镜像目录及其关系，只有取得相应权限和来源时保存。只采集必要字段，不原样保存带环境变量的完整inspect结果。内部组件通过明确镜像的采集能力或上传SBOM取得；工具/权限缺失时提供不可用原因和上传路径。
- ImageID、manifest digest、镜像索引、标签分别保存；同镜像可被多个实例引用。镜像SBOM不证明实例可写层、挂载卷及运行暴露已被检查。
- 软件SBOM继续使用现有对象/版本输入，不默认扫描主机应用目录，也不仅凭同名声明部署关系；主机关联需要明确用户提供或采集证明，并记录依据类型。
- 采集快照提供评估读取契约。已有软件/镜像SBOM评估继续复用；主机基础资料和包清单只有通过明确支持的后续适配器才能进入相应评估，不能直接塞进现有软件SBOM接口。
- 本规格不承诺新增通用Linux漏洞匹配引擎或全厂商EOS数据库；未支持资料显示“已采集、暂不支持此类评估”。评估开始必须是独立明确操作，绑定所选输入，不自动选择最新资料或累加历史。

## Testing Decisions

- 主验收边界沿用现有客户范围业务HTTP接口，覆盖三入口提交、任务、原始来源、归一化快照及评估读取交接；辅以少量关键浏览器流程。执行边界使用固定SSH/Pi进程替身，避免在线模型、网络主机状态和漏洞库变化影响普通自动验收。
- 已就上述边界向用户发出确认；它复用此前实现约定，而不是新增逐内部类的测试面。若用户在实现前提出调整，更新验收方式，不把未回复表述为新的明确批准。
- 好测试关注用户可观察的资料、归属、状态、版本与缺口，不固定内部目录、类名或函数调用次数。避免为简单映射重复制造实现镜像测试。
- 现有先例包括Windows脚本资料的原始输入/固定快照、CSV导入的事务与幂等、软件/镜像SBOM的来源与版本、客户对话的客户校验、Pi固定工具进程契约以及HTTP菜单兼容回归。
- 基础采集场景至少覆盖：未安装Trivy仍取得OS/包；dpkg或RPM格式中的版本/架构/状态；缺包管理器、部分命令失败、无权限、空/缺失清单、未知版本及乱码/坏结构。以未授权的系统查询作为可预测失败，不伪造完整覆盖。
- Docker场景区分CLI、包与daemon版本；无daemon权限仍保留基础资料，未单独发起时不执行容器内容获取。镜像身份、实例关系、SBOM与未覆盖可写层分别验收。
- Pi/SSH边界覆盖：固定工具与原句/所选范围绑定、越权目标/连接拒绝、主机身份不符、登录失败、命令超时、输出超限、结构伪造、模型未执行工具、Pi未配置、停止与重启。命令替身记录实际收到的固定能力，验证没有安装/提权或任意命令路径。
- 存储场景覆盖客户隔离、对象身份矛盾、幂等冲突、重启回读、事务失败、旧快照/评估不变、大清单边界及明细分页，不依赖生产资料。
- 浏览器至少覆盖三入口、Pi任务进度、部分结果、刷新回读、来源下钻、客户切换和HTTP环境全部菜单往返；凭据不进入URL或可见任务事件。
- 真实SSH只读账号、真实Pi与工具兼容验收需在实施阶段另有明确执行指令，使用已登记目标并记录实际版本/权限/范围。本规格发布不触发连接、扫描或工具安装。

## Out of Scope

- 本次规格发布不实现或部署采集器，不登录YS或客户目标，不执行Trivy、Docker或包查询，不修改账号权限。
- 不默认安装/临时下发Trivy，不自动sudo、修改组权限、启动/停止服务或修改目标文件；需要这些能力时另行设计和授权。
- 不建设任意远程shell、网络发现、批量网段扫描、漏洞利用或整改执行功能。
- 不在基础采集中自动读取全部容器内容、遍历应用目录、抓取运行内存或取得完整进程环境。
- 不承诺系统包清单覆盖手工软件和全部语言依赖，不把安装状态、镜像组件或工具成功退出直接当作运行适用性证明。
- 不新增通用Linux漏洞引擎、所有OS/包管理器支持、完整厂商生命周期源、Kubernetes采集、常驻Agent或全客户集中扫描平台。
- 不重写已有Windows输入、软件/容器SBOM评估、报告复核或公开情报流程；必要接缝扩展保持旧契约兼容。
- 不实现通用凭据保管库、交互式密钥部署、多人复核制度或新的账号体系。
