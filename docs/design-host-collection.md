# 主机资产采集讨论草案

日期：2026-11-19。状态：历史讨论草案，已综合为 [网页多入口采集规格](specs/web-asset-collection.md) 及 [GitHub #18](https://github.com/niwaip/ys/issues/18)。以下保留讨论过程；正式范围及未决项处理以发布规格为准，不执行主机扫描。

场景：以YS Linux主机为采集对象，取得主机信息、安装包及Docker资料，后续接收软件SBOM。以下为建议与已核实事实，不是已实现承诺。

## 能力分工

主机基本信息、系统包和可直接取得的软件版本优先由固定只读采集脚本取得，不依赖目标机安装Trivy。Trivy用于按需组件分析、SBOM生成或评估；不把它作为所有基础采集的前置条件。Docker CLI负责容器实例和镜像的实际关联；Trivy image负责明确镜像内容。后续用户上传的软件SBOM保留独立对象/版本，需要有依据才能关联为主机部署。

来源：
- https://trivy.dev/docs/latest/guide/target/rootfs/
- https://trivy.dev/docs/latest/guide/target/filesystem/
- https://trivy.dev/docs/latest/guide/supply-chain/sbom/
- https://trivy.dev/docs/latest/guide/target/container_image/
- https://docs.docker.com/reference/cli/docker/inspect/

## 建议采集包

同一次采集记录目标身份、时间、工具版本、范围、退出状态、缺口及各文件哈希。主机元数据、包清单、应用SBOM、Docker实例清单和按镜像身份生成的SBOM分文件保存，通过清单关联；不强制塞进单份SBOM。

主机名/IP只是属性；同名对象不能默认合并。容器ImageID、manifest digest和多架构index digest分别保存；标签变更不能覆盖旧输入。镜像发现不代表容器可写层或挂载数据目录已扫描；主机系统包、应用依赖、镜像依赖不合并计数。

仅保留所需Docker字段，不原样上传包含环境变量的inspect全集。缺失权限、未知版本、未采集路径均披露为缺口。

## 当前产品约束

现有文档已明确：软件/镜像CycloneDX JSON输入与评估可用；容器入口没有运行实例/主机关联。Linux主机统一采集快照、自动拆包接入和运行实例关系需要新增。当前SBOM限制500000字节、1000组件，真实主机或应用资料可能超限；不能截断后声称全量导入，也不应未经来源关联把系统包伪装成一份独立应用。

## 已确认的入口方向

用户明确要求多路径，当前优先通过Pi Agent发起采集。Pi是编排入口，与SSH、目标机本地运行、资料包上传不是互斥选项。建议Pi调用后端固定采集能力，能力根据目标连接配置选择执行方式；手工脚本和后续SBOM上传也接入相同来源/快照契约。这是设计方向确认，尚未授权或执行扫描。

用户进一步明确：在网页中直接完成操作，页面同时提供手动输入、上传脚本采集结果、调用Pi Agent采集。不是要求操作人员转到独立Pi终端。三入口共用客户/目标归属、核心校验、原始来源和采集快照；输入方式保留来源差异，不把全部原始资料强制压成相同字段。后续软件SBOM上传复用既有软件/镜像入口并关联明确对象与输入版本。

建议页面以“资产采集”组织，顶部明确当前客户和目标，下面三种输入方式。Pi页签允许描述范围，同时使用结构化的目标、连接配置和采集能力约束；Pi不从任意自然语言自行扩大目标或将SSH凭据放进提示词。后台保存任务进度、单项失败、产物、归一化结果和覆盖缺口，浏览器刷新后可回读。采集成功后的自动入库及是否继续评估尚待本轮确认。

Trivy rootfs处理执行位置可访问的根文件系统；标准用法中的SSH登录由外部执行器负责。可通过SSH在目标机运行Trivy，或在目标机生成SBOM后带回后台评估。Trivy client/server模式将本地分析结果发往扫描服务，仍需目标侧客户端分析文件，不意味着中央Trivy server可以直接遍历任意SSH主机。

参考：https://trivy.dev/docs/latest/guide/references/modes/client-server/

## 已确认的数据分层与采集边界

用户明确：收集产生基础数据，评估与收集分开；按照取得的内容分层。基础层直接取得OS、系统包和Docker版本。Docker内部内容独立获取、独立调用；软件组件分析通过提供SBOM进行。不会因基础采集而默认进入镜像内容分析或应用目录扫描。

1. 主机基础层：OS发行版、版本、运行内核、架构、硬件/网络可见信息；系统包名、完整版本、架构和安装状态。保留原始包管理器清单与来源，不强制生成SBOM。
2. 主机软件版本层：Docker等可直接识别的软件版本。客户端版本、已安装daemon包版本、实际运行daemon版本分别记录；无法访问daemon时不拿客户端版本替代。
3. 容器内容层：容器/镜像及其内部组件是独立目标；单独发起采集/提交镜像SBOM，权限不足时明确未取得。
4. 应用组件层：软件SBOM独立上传、关联明确对象与版本，不默认遍历主机应用目录。
5. 评估层：引用上述固定输入进行CVE/EOS/EOL判断，原始包清单不是完整应用依赖或运行适用性证明。

只读SSH账号可通过系统已有查询工具收集可读信息，无需安装Trivy。普通账号能读哪些文件、执行哪些命令由实际权限决定；SSH账号本身不等于强制只读，受控采集器只允许固定查询，不使用安装/修改命令。Docker daemon查询通常需要额外权限；不能为“只读”采集默认加入具备高权限的docker组。若需要运行daemon版本或容器元数据，应使用管理员预配置的受限查询能力或上传结果，不能自动提权。

## 后续待决定

1. 新目标接入：只选已有主机，还是同页允许新建待采集主机并绑定连接配置；建议两者均支持，目标与客户绑定后才启动固定工具。
2. Docker元数据边界：是否在基础采集中列出实例/镜像目录，还是所有容器内容一律从独立操作开始；镜像内部分析始终独立调用。
3. 只读账号策略：建议基础采集仅使用已有查询命令，不自动提权或安装；后续独立容器内容采集的额外权限另行配置。

确认本轮后再明确主机身份、应用目录、资料格式/大小、离线库更新与接入页面；届时记录已确认术语及必要的设计决定。

## 任务拆分期间的NetBox方向澄清

用户明确引入NetBox的动机是统一数据和结构、复用成熟资产管理，避免重复实现。原拟C01–C08尚未批准或发布；不能继续以本地资产主数据作为无需讨论的前提。已有ADR001仅记录此前首片选择，需对新的权威来源决定单独立项重审，不在讨论时静默改写既有决定。

建议待确认方案：NetBox成为资产主数据权威，复用Tenant、Device/VirtualMachine、接口/IP和Platform等成熟模型；YS网页和采集结果经受控适配关联NetBox身份，YS本地保留映射/缓存、不可变观测与评估/报告依据。软件包、容器实例、SBOM等需先核对实际NetBox版本及插件能力，再决定复用或保留必要的专用业务模型，不能声称均为NetBox原生能力。采集观测与资产当前配置的更新规则、权限与冲突策略仍需明确。

若采用此方案，先增加可演示的“从NetBox选择客户资产并在YS查看”的纵向任务，再安排写入/映射和旧记录迁移；按此重排采集票。当前只记录方向，不修改GitHub父规格、不发布任务、不连接或修改NetBox。
